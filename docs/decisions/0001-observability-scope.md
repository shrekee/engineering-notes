# ADR 0001：普通容器日志与 Pod 监控的边界

- 日期：2026-10-29
- 状态：参考方案；未部署、未验收

## 背景

日志查询、资源监控和分布式追踪经常被合称为“可观测性”，但数据来源、交付语义和运维成本不同。若不先限定问题，很容易得到功能很多却无法说明数据完整性的系统。

## 决策

1. 先复用已有平台；只有明确缺口才增加组件。
2. 日志以 Loki 为参考后端，指标以 Prometheus 为参考管线，Grafana 为统一查询界面。
3. 保留 LoongCollector 作为应用文件与容器发现的候选路径；stdout/stderr 可采用 Alloy，依据权限与开销选择 API 或文件方式。
4. Events 作为可选上下文；本阶段不建设 tracing、profiling、自动 RCA，也不宣称端到端 exactly-once。
5. 先完成发现、轮转、恢复、查询、权限和覆盖验收，再扩展来源和规模。

这是一组设计选择，不是产品优劣排名，也不代表任何实际集群已经满足条件。技术依据见[架构](../observability/architecture.md)与[来源](../observability/sources.md)。

## 权衡与被暂缓的方案

双采集器可能适应不同来源，但增加版本维护与重复采集风险；必须为每个来源指定唯一责任通路。全部切换到单一采集器能减少组件，却可能扩大迁移范围，不能在缺乏文件发现和恢复测试时直接采用。已有 Fluent Bit 或 Vector 若满足验收，也不应只为统一名称而替换。

自建全套后端带来存储、容量、保留和安全运维责任，因此不作为默认起点。引入 tracing 必须有独立问题定义、采样与上下文传播设计，而不是将 Events 改名为“链路”。

## 重新评估条件

目标运行时或安全策略改变、输出插件无法满足验证、采集成本超出预算、已有平台出现明确缺口，或业务提出跨服务请求分析需求时，新增或修订 ADR。变更需附公开依据或可公开的合成实验结果，并更新验收清单；不能用本参考决策代替真实环境评审。
